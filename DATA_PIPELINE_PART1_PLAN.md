### Phase 1.2 Proposal Details (Confirmed in Phase 1.3)

The user confirmed the following recommendations in Task 1.3. `CONTEXT.md` has no dedicated data-pipeline “KPIs to Measure” or “Destination table” sections, so preserve the distinction between these confirmed project decisions and verbatim briefing requirements.

- **Proposed purpose sentence:** Produce a weekly Customer Support performance rollup for Roberto Díaz and Laura Mendoza's weekly executive report, calculating 24-hour SLA attainment, average resolution time, eligible-query automation resolution, and end-of-week support backlog from `support_ticket_resolved`, `support_query_closed`, and `support_queue_snapshot_recorded`.
- **Audience and business use:** Roberto Díaz is the primary audience for support delivery and workload; Laura Mendoza is the secondary audience for weekly executive review. The rollup should show whether the service is meeting the 24-hour commitment, whether chatbot automation is progressing toward the 40% target, and what queue state was reported at week-end. The 48-hour resolution time and 24-hour SLA are context baselines/targets, not this pipeline's computed results.
- **Proposed KPI formulas and edge cases:**
  - **SLA attainment rate:** `100 * sla_met_ticket_count / resolved_ticket_count`. From `support_ticket_resolved`, accept nonempty `ticketId`, `slaTargetSeconds == 86400`, and a boolean `slaMet`. The denominator is distinct valid `ticketId` values per reporting week; the numerator is the subset with `slaMet == true`. First deduplicate delivery retries by envelope `eventId`; within a week count each ticket once using its latest valid resolution event by `resolvedAt`. Return numerator and denominator. With a zero denominator, return null plus `no_data`, not zero percent. This measures performance against the 24-hour commitment.
  - **Average resolution time:** `sum(resolutionSeconds) / resolved_ticket_count`, returned in seconds and hours. Use the same latest-per-ticket weekly set, requiring finite `resolutionSeconds >= 0` and the 24-hour target. Return valid sample count; with no valid tickets, return null plus `no_data`. This makes progress against the stated 48-hour current average measurable.
  - **Eligible-query automation resolution rate:** `100 * bot_resolved_eligible_query_count / eligible_query_count`. From `support_query_closed`, the denominator is distinct nonempty `queryId` values with `eligibleForAutomation == true`; the numerator is the subset with `resolved == true` and `resolutionMethod == "bot"`. Use envelope `timestamp` as the close-event time because this payload has no `closedAt`. Deduplicate transport retries by `eventId`, then count one outcome per query per reporting week. Return numerator and denominator; if denominator is zero, return null plus `no_data`. Compare with the 40% target in `CONTEXT.md`.
  - **Week-end queue backlog:** For each `queueId`, select the latest `support_queue_snapshot_recorded` with envelope `timestamp` at or before the period end. Preserve `openTicketCount`, `overdueTicketCount`, `unassignedTicketCount`, `activeAgentCount`, and `oldestOpenAgeSeconds` as point-in-time values, never weekly sums. Include `snapshot_at` and snapshot age. Proposed freshness rule: mark the row stale when the snapshot is more than five minutes before period end; if no fresh snapshot exists, report missing/stale rather than zero. Do not sum values across queues, especially `activeAgentCount`, unless operations confirms queues are mutually exclusive.
- **Proposed period and schedule:** Use Monday 00:00 through the following Monday 00:00 in `Europe/Madrid`, with an exclusive upper bound and source timestamps normalized to UTC. Run Monday at 06:00 `Europe/Madrid` for the previous completed week and publish only after success. This aligns to Valencia headquarters and the weekly executive report; timezone and run time still require confirmation.
- **Freshness limitation:** `CONTEXT.md` also requests real-time support and executive dashboards, while this proposed rollup is weekly. The proposed KPI endpoint can expose the latest completed week with `generated_at` and period metadata, but cannot claim real-time data. Confirm whether this is acceptable for the Part 3 dashboard or whether v1 needs a more frequent materialization. The weekly pipeline does not replace operational streams.
- **Proposed destination tables and grain:** The supplied briefing has no exact destination names; the user confirmed these names for the design. Under the `reporting` schema, use `reporting.support_performance_weekly` with one company-wide row per week (`period_start` key); `reporting.support_queue_weekly` with one row per week and `queueId` (`period_start`, `queue_id` key); `reporting.pipeline_runs` with one row per `run_id`; and user-approved `reporting.pipeline_run_events` to map contributing source events to each run and output key.
- **Proposed reporting endpoints and function mapping:** `GET /reporting/status` calls `get_latest_run_status()`; `POST /reporting/runs` calls `trigger_support_performance_flow(...)` and returns/associates a unique `run_id`; `GET /reporting/kpis` calls `query_support_performance_kpis(period_start, period_end, queue_id=None)`. Put these functions in a proposed `data/pipelines/support_performance.py`; keep them outside the telemetry service and keep ETL/KPI calculation out of `services/reporting/`.
- **Known metric-definition limit:** The schema has `ticketId` but no resolution-cycle ID, and `queryId` but no query-close-cycle ID. The proposal counts each ticket/query once per reporting week. If reopened/repeated resolution cycles must count separately, request approval for an additive stable cycle identifier before design; do not infer one from `eventId` or `requestId`.
- **Proposed v1 exclusions:** Do not include `support_dissatisfaction_detected` or `support_ticket_escalated` in this rollup unless an approved KPI and business action require them; their stream use for timely intervention remains separate.

### Task 1.1 Evidence

- `CONTEXT.md` (Customer Support and Executive Direction): Roberto Díaz leads 30 support agents; the stated current average resolution time is 48 hours against a 24-hour SLA. The support needs include a chatbot target of 40% of queries resolved without human intervention, a real-time support dashboard, and ticket sentiment detection before escalation. Laura Mendoza receives weekly manually prepared reports and needs a unified executive dashboard and automated weekly report. These are briefing context, not proof of actual measured telemetry values.
- `docs/telemetry/event-schemas.json` defines the required envelope as `eventId`, `timestamp`, `sessionId`, `userId`, `event_type`, `schemaVersion`, `requestId`, and `properties`. `timestamp` is occurrence time normalized to UTC. The support event payloads are:
  - `support_ticket_resolved`: `ticketId`, `clientId`, `channel`, `openedAt`, `resolvedAt`, `resolutionSeconds`, `slaTargetSeconds` (constant 86400), and `slaMet`.
  - `support_queue_snapshot_recorded`: `queueId`, `openTicketCount`, `overdueTicketCount`, `unassignedTicketCount`, `activeAgentCount`, and `oldestOpenAgeSeconds`.
  - `support_query_closed`: `queryId`, `eligibleForAutomation`, `resolutionMethod` (`bot`, `agent`, or `unresolved`), `humanHandoff`, and `resolved`.
  - `support_dissatisfaction_detected`: `ticketId`, `clientId`, `sentimentScore`, `riskLevel`, and `modelVersion`.
  - `support_ticket_escalated`: `ticketId`, `escalationType`, and `escalationReasonCategory`.
- `docs/telemetry/telemetry-plan.md` classifies these support events as streams. It says to deduplicate retries by `eventId`; retain distinct resolution/escalation/dissatisfaction/query outcomes; throttle replaceable queue snapshots to at most one per queue per 30 seconds while retaining the latest; and use rolling 15-minute windows for the automation rate. Customer/ticket/query identifiers must be pseudonymous; never report ticket/query content, and keep IDs out of exposed business metrics where possible.
- `services/telemetry-api/app/routers/telemetry.py` validates the envelope (`eventId` maps to internal `event_id`; `requestId` to `request_id`) and `map_event_to_row` copies `properties` into `tags`, removes reserved `value` and `message` from that JSON object, then adds `tags.event_id`. The mapped row contains `event_type`, occurrence `timestamp`, `service`, `tags`, `level`, `value`, and `message`. The mapped row does not persist `requestId`, `sessionId`, `userId`, or `schemaVersion` as columns or tags.
- `services/telemetry-api/app/db.py` inserts those mapped fields into `public.telemetry_events` and ignores conflicts on `tags.event_id`. `services/telemetry-api/migrations/001_create_telemetry_events.sql` defines `id`, `event_type`, `timestamp` (`TIMESTAMPTZ`), `service`, `tags` (`JSONB`), and `level`; it has a unique index on `tags ->> 'event_id'`. `services/telemetry-api/migrations/003_add_telemetry_value_message.sql` adds the nullable `value` and `message` columns. There is no separate received-at timestamp; `id` is an insertion sequence, not a timestamp.
