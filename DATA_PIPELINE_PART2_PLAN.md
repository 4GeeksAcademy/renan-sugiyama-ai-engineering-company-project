- **Business output:** weekly Customer Support performance rollup for Roberto Díaz and Laura Mendoza, using the approved weekly period Monday 00:00 through the following Monday 00:00 in `Europe/Madrid`, stored/queryable as UTC boundaries. Schedule: Monday 06:00 `Europe/Madrid`; recompute the newly completed week plus four preceding completed weeks.
- **Read-only input:** `public.telemetry_events`, columns `event_type`, `timestamp`, `tags` (`JSONB`). Use only `support_ticket_resolved`, `support_query_closed`, and `support_queue_snapshot_recorded`; stored retry ID is `tags.event_id`. Do not assume `received_at`, `requestId`, or `id` is available to the reader.
- **Ticket KPIs:** from `support_ticket_resolved`, require nonempty `ticketId`, `slaTargetSeconds == 86400`, and valid payload values. Deduplicate transport retries by `event_id`, then use the latest `resolvedAt` per `ticketId` per week. SLA attainment is true `slaMet` tickets / valid resolved tickets; average resolution time uses finite nonnegative `resolutionSeconds`, returned in seconds and hours. Include counts; a zero denominator is `null` with `no_data`, never zero percent.
- **Automation KPI:** from `support_query_closed`, use envelope `timestamp`, one latest outcome per nonempty `queryId` per week, and `eligibleForAutomation == true` as the denominator. The numerator additionally requires `resolved == true` and `resolutionMethod == "bot"`. Include numerator/denominator and use `null` plus `no_data` when the denominator is zero.
- **Queue KPI:** from `support_queue_snapshot_recorded`, select the latest observation per observed `queueId` at or before period end. Keep `openTicketCount`, `overdueTicketCount`, `unassignedTicketCount`, `activeAgentCount`, and `oldestOpenAgeSeconds` as point-in-time values, with `snapshot_at`, age, and freshness. A snapshot older than five minutes is stale; missing/stale is not zero. Do not sum `activeAgentCount` across queues.
- **Approved tables:** `reporting.support_performance_weekly` keyed by `period_start`; `reporting.support_queue_weekly` keyed by `(period_start, queue_id)`; `reporting.pipeline_runs` keyed by `run_id`; and restricted `reporting.pipeline_run_events` keyed by `(run_id, event_id)`. Preserve audit history and do not expose source IDs in business API responses.
- **Approved flow/tasks:** `support_performance_flow`; `extract_support_events`, `transform_support_metrics`, `load_reporting_partitions`. The design places importable pipeline functions in `data/pipelines/support_performance.py`; keep `data/pipelines/pipeline.py` as the requested executable CLI entry point and thin integration layer, not a second ETL implementation.
- **Approved API:** in a separate `services/reporting/` module, `GET /reporting/status`, `POST /reporting/runs`, and `GET /reporting/kpis`, mapped respectively to `get_latest_run_status()`, `trigger_support_performance_flow(...)`, and `query_support_performance_kpis(...)` in `data/pipelines/`. The KPI endpoint reads reporting outputs only.

The design also requires an external source/capture-health signal to distinguish a healthy empty source from silence. No provider or signal contract is present in the repository. Until the owner identifies/provisions it, represent source health as `unknown`, never assert a true zero, and do not fabricate a provider or health endpoint.
